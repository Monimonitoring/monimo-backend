## 2부 : 고도화 뒤 쓸 수 있는 이력서

> 여기 있는 줄은 **아직 쓰면 안 된다.** 고도화를 끝내고 `before → after` 를 재야 참이 된다.
> `N` · `M` 자리에 실측값을 넣는 순간 1부로 옮긴다.

- 읽는 법
  - 각 묶음 머리의 `[고도화 뒤 · 아직 안 함]` 은 **붙여 넣을 때 지우는 표시**가 아니라 지금은 거짓이라는 뜻이다
  - 지금 값(`before`)이 이미 있는 줄은 그 숫자를 적어 뒀다. 없는 줄은 `[측정 필요]`

### 묶음 A : Kafka 수집 경로 처리량과 전송량 튜닝

```
[고도화 뒤 · 아직 안 함]
Kafka 수집 경로 처리량 개선
파티션 3개를 컨슈머 1개가 스레드 하나로 순차 처리하던 구조를 컨슈머 동시성 3으로 올려 병렬도 1 → 3, 같은 부하에서 consumer lag N → M, 적재 처리량 N건/초 → M건/초
수집기 프로듀서에 배치(linger.ms · batch.size)와 zstd 압축을 적용해 Kafka 전송 바이트 N MB/일 → M MB/일, 프로듀서 요청 수 N → M 감소
우리가 만든 APM 자신이 수집 경로의 lag 과 적재 지연을 보도록 자기 감시 지표를 붙여, 적재 지연 발견 시간 N분 → M분 단축
```

- 지금 값
  - 토픽 `raw` 파티션 3개 · `raw.dlq` 1개 (`compose.yaml:71`)
  - Ingester 컨슈머 동시성 설정 0줄 = 기본 1
    - 컨슈머가 하나라 **파티션 3개를 다 할당받기는 한다**. 문제는 그 셋을 스레드 하나가 순차로 처리하는 것이다 (병렬도 1)
  - 프로듀서에 `compression.type` · `linger.ms` · `batch.size` 설정 0줄
  - **건드리면 안 되는 것** : `listener.ack-mode: RECORD` 는 `#187`(집계 중복 정리)이 재처리 양을 최대 500 레코드에서 1 레코드로 줄이려고 **일부러 고른 값**이다
    - 배치 컨슈밍으로 바꾸면 그 1 레코드가 다시 batch 단위로 돌아가 1부의 성과를 스스로 지운다
    - 그래서 A 는 **동시성과 프로듀서 설정만 더한다**. 교체가 아니라 추가다
  - 레코드 하나가 스팬 평균 90줄 · 최대 512줄 (`195-dlq-reprocess/README.md:152`)
  - 부하 수단은 이미 있다 : k6 초당 주문 20건에서 스팬 339개/초
- 재는 방법
  - `before` : 지금 설정으로 k6 를 초당 40건까지 올리며 consumer lag · 적재 처리량 · 토픽 바이트를 잰다
  - `after` : 컨슈머 동시성 · **프로듀서** 배치 · 압축을 넣고 같은 부하로 다시 잰다 (컨슈머 쪽 배치는 위 「건드리면 안 되는 것」 때문에 손대지 않는다)

### 묶음 B : 프로파일링 기반 오버헤드 절감

```
[고도화 뒤 · 아직 안 함]
에이전트 · 수집기 CPU · 메모리 오버헤드 절감
설정 넷(전송 간격 · 샘플링 · 배치 크기 · 배치 주기)을 85회차 측정해 CPU 가 전혀 줄지 않음을 확인한 뒤, async profiler 로 계측 경로의 CPU 상위 함수를 찾아 주문 1건당 추가 CPU +3.37ms → +M ms 절감
힙 덤프로 에이전트 메모리 +80 ~ 141MB 중 힙 아닌 쪽 +45 ~ 53MB(클래스 +5,131 ~ 5,683개 · JIT 코드)의 실제 구성을 분해해, 계측 범위 조정으로 메모리 N MB → M MB 절감하면서 빠지는 지표를 84건 → M건으로 축소
수집기 쪽도 같은 방법으로 프로파일링해 스팬 1건당 처리 CPU N ms → M ms 단축
```

- 지금 값
  - 에이전트 붙임 대가 : CPU 1코어 대비 +0.6 ~ +3.6%p · 메모리 +80 ~ 141MB (`monimo-shop` `#36`)
  - 주문 1건당 CPU : 뗌 16.61ms → 붙임 19.98ms (+3.37ms · +20%) (`monimo-shop` `#51`)
  - 설정으로 줄이는 길은 닫혔다 : 전송량 91배 줄여도 CPU 가 회차 폭 안에서 안 움직였다
  - 계측 범위 축소로만 약 20MB 줄지만 메트릭 84건이 빠진다
  - 메모리 안쪽 구성도 이미 쟀다 : 힙 아닌 쪽 +45 ~ 53MB · 클래스 +5,131 ~ 5,683개 (`monimo-shop/docs/seungjo/36-agent-overhead/results.md:40,45`)
  - 부하별 k6 p95 도 있다 : 초당 10 · 20 · 40건에서 붙임 / 뗌 = 19.4/18.8 · 17.2/12.8 · 13.8/10.7ms (같은 파일 `:23`)
  - **그래서 다음 질문이 「어느 함수인가」 로 정해져 있다**
- 재는 방법
  - `before` 가 이미 있다 (`#36` 5회차 · `#51` 85회차). 같은 스크립트 `perf/overhead/` 를 그대로 쓴다
  - async profiler 로 flame graph 를 떠 상위 함수를 지목하고, 그 함수를 피하는 설정이나 코드로 바꾼 뒤 같은 회차로 다시 잰다

### 묶음 C : 배포 중 무중단과 연쇄 장애 차단

```
[고도화 뒤 · 아직 안 함]
배포 중 메시지 유실 방지와 연쇄 장애 격리
배포 시 컨슈머가 처리 중인 메시지를 버리던 것을 graceful shutdown(SIGTERM 유예 + 처리 완료 후 커밋)으로 바꿔, 배포 1회당 재처리 메시지 N건 → M건, 리밸런스 시간 N초 → M초 단축
저장소 장애가 수집 경로 전체를 막지 않도록 ClickHouse · PostgreSQL 호출에 차단기와 격벽을 적용해, 저장소 정지 중 수집기 OTLP 응답 지연 N초 → M초로 격리
쿠버네티스 배포에 롤링 업데이트와 probe 유예를 맞춰 배포 중 수집 누락 구간 N초 → M초
```

- 지금 값
  - `server.shutdown: graceful` 0줄 (레포 다섯 전체) · `terminationGracePeriodSeconds` 0줄 · `strategy` 0줄(기본값으로 돈다)
    - **매니페스트와 probe 셋은 이미 있다** (`monimo-deploy/apps/{collector,ingester}/deployment.yaml` 의 startup · liveness · readiness)
    - 비어 있는 것은 종료 유예와 롤링 전략뿐이다
  - 리밸런스 시간은 재 둔 것이 있다 : 같은 그룹 되넣기에서 211 · 229밀리초 (`195-dlq-reprocess/README.md:152`)
  - 저장소 장애 격리는 반쪽이다 : 적재 실패 3단 · DLQ · `socketTimeout` 10초는 있으나 **차단기는 알림 파트에만 있고 수집 경로에는 없다**
  - PG 가 멈췄을 때 게이지만 올라가고 카운터는 35초 동안 안 움직였다 (`127-jdbc-socket-timeout/README.md:86`)
- 재는 방법
  - `before` : 부하를 흘리는 중에 `kubectl rollout restart` 로 재배포하고 재처리된 메시지 수 · 리밸런스 시간 · 수집 누락 구간을 잰다
  - `after` : graceful shutdown · 차단기 · probe 유예를 넣고 같은 절차로 다시 잰다
- 조건
  - **배포 계획 4 ~ 5단계(Terraform · ECR)가 끝난 뒤에만 참이 된다.** 그 전에는 로컬 클러스터에서 리밸런스 · 차단기까지만 잴 수 있다
  - 일정은 이미 밀렸다 : `plan.md` 는 4단계를 11/1 ~ 6 으로 잡았는데 오늘(11/13)까지 `.tf` 가 0개다. 날짜가 아니라 **선행 단계**로 조건을 적는다
