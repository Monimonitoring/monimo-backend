# 경보 사건 발행을 CDC 로 — 격리 실험 (장애 네 가지 · 폴링 릴레이와 비교)

> 2026-10-28 실측, 학습 · 판단용. 운영 적용 없음. 도구 `experiments/cdc/`. 원본 로그는 실험 직후 임시 폴더에 있다가 재부팅으로 지워졌다 — 아래 숫자는 그때 `cdc_analyze.py` 가 낸 요약을 옮긴 것이다(`experiments/cdc-results/README.md`).
> 출발선은 `100-outbox-polling.md` : 지금 알림 지연의 대부분은 그룹 대기(10초)이고 폴링 몫은 작다. 그래서 여기서는 "CDC 가 빠른가" 보다 **CDC 가 무엇을 지키고 무엇을 새로 요구하는가** 를 본다.

## 1. 무엇을 만들었나

발송 큐(`notification_outbox`)를 CDC 로 바꾸지 않았다. 그 큐는 그룹 대기 · 예약 시각 · 재시도 · 선점과 임대 · 발화 → 복구 순서 · 결과 기록을 맡고 줄이 계속 UPDATE 된다. Debezium 의 Outbox Event Router 는 INSERT 만 이벤트로 본다. 그래서 **바뀌지 않는 사건 기록(FIRED · RESOLVED)만 따로 발행**하고, 발송 상태는 지금처럼 발송 큐가 맡는 구조를 격리 환경에 만들었다.

```
생산자(Detector 흉내) TX ─ alert_events INSERT + alert_event_outbox INSERT → COMMIT
   → PG WAL (wal_level=logical, 슬롯 alert_outbox) → Debezium 3.6.2 (Outbox Event Router, 키 = 사건 id)
   → Kafka alert.events.cdc (파티션 3)
   → 소비자 ① 발송 작업 delivery_jobs (UNIQUE event_id · 채널) / ② 사건 이력 event_history
비교 : 같은 이벤트를 alert_event_outbox_poll 에 넣고 폴링 릴레이(1초 · 0.2초)가 같은 Kafka · 같은 소비자로
```

| 항목 | 값 |
|---|---|
| 환경 | `experiments/cdc/compose.yml` (프로젝트 `monimo-cdc`, PG 17.11 · Kafka 3.9.2 · Debezium Connect 3.6.2.Final). 팀 PG 는 `wal_level=replica` 라 따로 띄웠다 |
| 소비자 | 메시지마다 PG 에 `ON CONFLICT DO NOTHING` 으로 넣고 커밋한 **뒤에** 그 메시지의 오프셋만 커밋 |
| Connect 오프셋 저장 | 이미지 기본값(60초 주기) 그대로 |
| 시각 | 생산자 = DB 커밋 완료 응답을 받은 직후, 소비자 = 메시지를 받은 순간. 둘 다 호스트 시계 |

## 2. 장애 네 가지

| 실험 | 결과 |
|---|---|
| E1 이벤트까지 넣고 ROLLBACK (커밋 20 · 롤백 20) | 커밋 20 모두 받음, **롤백 20 중 0** |
| E2 커밋 직후 생산자 종료 (20번) | PG 에 남은 20 모두 받음 |
| E3 초당 20건 넣는 중 Connect `docker kill` → 60초 뒤 start | 2,400 중 **커밋된 이벤트의 누락은 관측되지 않았다**. **73건을 두 번** 받았다 — 모두 kill 0.4 ~ 4.0초 전에 커밋된 것(Kafka 에는 보냈지만 Connect 가 오프셋을 아직 남기지 못한 구간). 소비자가 걸러 발송 작업은 이벤트당 1줄 |
| E4 소비자가 작업 저장 뒤 · 오프셋 커밋 전 종료 | 그 1건(오프셋 846)을 다시 받았고(새로 넣음 0), 발송 작업 30줄 · 이벤트당 1줄 |

E3 의 시간 · 디스크 :

- kill 뒤 60초 동안 이벤트는 PG 에만 쌓였다(1,807건). 두 시간 모두 **`docker start` 부터** 쟀다 : 커넥터가 RUNNING 이 되기까지 **약 40초**(Connect 워커 기동 · 재배정), 쌓인 것을 다 받기까지 **약 46초**. 46초는 40초를 포함한다 — 밀린 1,807건을 비우는 데 든 시간은 약 6초다
- 슬롯이 붙잡은 WAL 은 `pg_current_wal_lsn() − restart_lsn` **LSN 차이**로 쟀다(실제 디스크 점유가 아니다. 같은 동안 `pg_wal` 폴더는 세그먼트 단위라 최대 16MB). 멈추기 전 최대 573KB → 멈춘 동안 최대 **2.1MB**(kill 뒤 115초), 초당 약 19KB. 초당 20건이 하루 이어진다고 가정하면 약 1.6GB 가 지워지지 않고 남는다는 계산이다(선형 외삽, 실측 아님). 커넥터가 멈춰도 슬롯은 남아 WAL 을 붙잡는다 — 감시 · `max_slot_wal_keep_size` 상한이 필요하다

### 첫 실행에서 찾은 소비자 버그

첫 실행의 E4 에서 소비자가 **2건을 다시 받지 못했다**. 파티션 2 오프셋 834 를 처리하다 죽었는데, 재시작한 소비자는 837 부터 읽었다(835 · 836 건너뜀).

원인 : `kafka-python` 의 `consumer.commit()` 을 인자 없이 부르면 **라이브러리가 관리하는 소비 위치**를 커밋한다. `poll()` 로 여러 레코드를 받아 차례로 처리하는 구현에서는 그 위치가 DB 처리를 끝낸 위치보다 앞설 수 있다. 라이브러리는 DB 저장이 끝났는지 모른다.

그때는 끄지 않고 남아 있던 다른 실험의 소비자가 같은 표에 그 이벤트를 넣어서, **발송 작업 총 개수가 맞아 보였다.** 총 개수로 성공을 판정한 탓에 누락과 실험 간 간섭이 함께 가려졌다.

고친 것(`consumer.py`)과 원칙 :

- 자동 커밋을 끈다
- DB 작업이 성공한 **뒤** 커밋한다
- 파티션별로, 연속해서 처리가 끝난 마지막 오프셋의 **다음 값(+1)** 을 커밋한다. 병렬로 처리한다면 가장 큰 완료 오프셋을 그냥 커밋하면 안 된다
- 중복 제거 기록과 발송 작업 생성은 같은 DB 트랜잭션으로 한다

판정도 바꿨다 : 총 개수가 아니라 **예상 이벤트 id 집합 ↔ 소비자별 처리 이벤트 id 집합 ↔ 생성된 발송 작업의 이벤트 id 집합**을 비교한다. 위 표가 고친 소비자로 다시 돌린 결과다. CDC 가 "최소 한 번" 을 지켜도 소비자가 오프셋을 잘못 다루면 그 앞에서 잃는다.

## 3. 전달 지연 · 유휴 DB 비용 (같은 Kafka · 같은 소비자)

커밋 → 소비자가 받음, ms

| 경로 | 한 건씩 30 중앙값 | p95 | 최대 | 초당 20건 60초 중앙값 | p95 | 최대 | 유휴 PG 트랜잭션/초 | 유휴 읽은 줄/초 |
|---|---|---|---|---|---|---|---|---|
| CDC (Debezium 기본) | 462 | 817 | 855 | 540 | 883 | 1,030 | 0.5 | 25 |
| CDC `poll.interval.ms=50` | 79 | 155 | 202 | 59 | 99 | 350 | 0.8 | 148 |
| 폴링 릴레이 1초 | 493 | 997 | 1,023 | 550 | 998 | 1,242 | 1.6 | 29 |
| 폴링 릴레이 0.2초 | 119 | 204 | 217 | 111 | 206 | 302 | 5.3 | 25 |

- **Debezium 기본 설정은 1초 폴링과 지연이 비슷했다.** `poll.interval.ms`(커넥터가 새 변경 이벤트를 기다리는 간격, 기본 500ms)를 50ms 로 바꾸자 전달 지연이 줄었다(중앙값 59 ~ 79ms, 초당 20건 p95 99ms 로 네 경로 중 가장 짧음). 이번 환경에서는 이 설정이 지연에 영향을 줬다. 전체 지연이 이 설정 하나로 정해지는 것은 아니다
- 유휴 상태의 PG 트랜잭션 증가량은 CDC 가 더 작았다(조회하지 않는다). 전체 CPU · I/O · 메모리 비용은 비교하지 않았다. 다만 `poll.interval.ms=50` 은 유휴 읽은 줄이 초당 148 로 늘었다 — 무엇이 읽는지는 나누지 않았다
- 성능 차이는 실제로 관측됐다(CDC 50ms p95 99ms vs 폴링 0.2초 206ms, 각 1회). 다만 지금 알림은 그룹 대기 10초를 두므로, 이 차이가 현재 서비스에 충분히 중요한지는 따로 판단할 문제다(§4)

## 4. 판단

- **지금 알림 경로(Detector → 발송 큐 → Notifier)는 폴링을 유지한다.** CDC 구현과 장애 검증은 마쳤지만, 현재 그룹 대기 정책과 지연 요구에서는 전달 지연 감소만으로 전환 비용을 정당화하기 어려웠다. 발송 큐의 재시도 · 그룹 마감은 CDC 가 대신하지 않는다
- **CDC(또는 Kafka 발행)를 검토할 때** : 사건 이력 · 분석 · 감사처럼 **발송과 독립된 소비자가 생기고, 각자 자기 속도로 재처리해야 할 때**. 여러 소비자 · 재처리는 Kafka 의 이점이고 CDC 는 그 Kafka 로 옮기는 방법 중 하나다 — 폴링 릴레이로도 같은 요구(최소 한 번, 소비자가 걸러야 함)를 구현할 수 있지만, 이번에는 릴레이 장애 때의 보장을 검증하지 않았다
- CDC 를 붙이면 새로 생기는 일 : Connect 클러스터 운영(이번 재시작 40초), 복제 슬롯 · WAL 보관 감시, 커넥터 재시작 때의 중복(이번 73건)을 소비자가 걸러야 함, 오프셋을 메시지 단위로 커밋하는 소비자
- **다시 검토할 조건** : 긴급 경보처럼 그룹 대기를 건너뛰고 짧은 시간 안에 보내야 하는 요구 · 자동 대응 같은 다른 소비자에게 사건을 바로 넘겨야 할 때 · 서비스와 워커가 늘어 반복 조회가 실제 DB 병목으로 보일 때 · 여러 서비스의 이벤트 발행을 공통 CDC 로 운영해야 할 때. 그때는 예상 이벤트율 · 순간 몰림 · 워커 수를 먼저 정하고, 같은 요구 아래 폴링과 CDC 의 지연 · DB CPU · I/O · 전체 자원 · Connector 복구 시간 · WAL 증가를 비교한다

## 5. 한계

맥북 한 대 · 각 실험 1회 · 생산자는 파이썬 흉내(실제 Detector 아님) · 파티션 3 · 단일 Kafka 브로커 · Connect 워커 하나. 파티션 안 순서와 실제 Slack 발송 완료 순서의 관계, 발송 큐로 넘긴 뒤의 그룹핑은 재지 않았다. PG 장애 · Kafka 장애 · 슬롯 상한 초과(`max_slot_wal_keep_size`) 때의 동작도 재지 않았다.

- 발송 작업이 이벤트당 1줄이라는 것과 Slack 에 정확히 한 번 도착한다는 것은 다르다. 이번에는 발송 작업까지만 봤다
- 회차 격리가 덜 됐다 : consumer group 은 회차마다 다르지만 출력 표는 회차마다 나누지 않았다. 다음에는 run_id 로 데이터 범위를 나누고, 시작 전에 남은 실험 소비자가 없는지 검사한다
- p95 는 각 1회 결과다. CDC 50ms 의 p95 99ms 로 "100ms 를 안정적으로 보장한다" 고 말할 수는 없다
