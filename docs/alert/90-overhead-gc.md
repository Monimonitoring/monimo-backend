# 에이전트 · 스레드 덤프가 order JVM 에 주는 GC · 지연 비용

> 2026-10-28 실측, `#260`. 도구 `experiments/overhead_gc*`, 원본 `experiments/gc-results/2026-10-28-overhead/`.
> CPU · 메모리 비용과 줄이는 설정은 수집 파트(승조)가 쇼핑몰 `perf/overhead/`(shop `#36` · `#51`)로 쟀다. 여기서는 같은 출발선에 GC · 요청 지연 · 덤프만 더했다.

## 1. 왜 쟀나

GC 경보(`80-gc-time.md`)가 보는 GC 값은 **에이전트를 붙인 JVM 의 값**이고, 경보가 열리면 부르는 스레드 덤프도 대상 JVM 안에서 돈다. 쇼핑몰 측정에는 GC 시간 · 요청 지연 · 덤프 순간의 비용이 없었다.

## 2. 조건

| 항목 | 값 |
|---|---|
| 출발선 | 쇼핑몰 `perf/overhead/` 그대로 : 네 서비스 각각 CPU 1 · 메모리 1GB(`limits.yml`), 뗌은 `no-agent.yml`(entrypoint `java -jar`), 워밍업 40초 |
| 더한 것 | order 만 `overhead_gc_override.yml` : G1 · `-Xms256m -Xmx256m` · `-Xlog:gc*,safepoint`. 전송 간격은 그대로(10초) |
| 부하 | k6 `order.js` 초당 주문 40건(iteration, HTTP 는 약 1.5배) · 300초 |
| 조건 | `off` 뗌 · `on` 붙임 · `dump` 붙임 + 측정 중 30초마다 Collector `POST /internal/thread-dump` 직접(회차당 10번, API server 를 거치지 않아 5분 쿨다운 없음) |
| 반복 | 세 조건 × 5회, 반복마다 순서를 한 칸 돌림 |
| 환경 | 맥북 한 대 · Docker Desktop. shop `6eff687` · backend `971be04` |
| 버린 회차 | 첫 `r2-on` · `r2-dump` : 10:16:48 KST 덮개를 닫아 잠듦(배터리). r2-on 은 측정 끝 18초 겹침, r2-dump 는 VM 이 멈춰 벽시계 635초 건너뜀. `caffeinate` · 전원 연결로 r2 ~ r5 를 다시 돌렸다 |

덤프 창 = 덤프 요청부터 응답 + 1초(중앙값 1,397ms). `off` · `on` 에도 같은 자리(측정 시작 15초 뒤부터 30초마다) · 같은 길이의 창을 둔다.

## 4. 읽는 법

- **에이전트 → GC** : 할당 속도 · GC 횟수는 5회 모두 범위가 안 겹친다. GC 시간 합은 1분 환산 약 254 → 462ms(10% 기준 6,000ms 대비 작지만 이 부하의 GC 를 거의 두 배로). 단 off 최대 1,867 · on 최소 1,873 으로 6ms 차이라 합은 횟수만큼 뚜렷하지 않다
- **에이전트 → 지연** : p95 는 같은 반복 안에서 5회 모두 on > off. GC 때문인지 계측(스팬 생성) 자체 때문인지는 나누지 않았다
- **덤프** : 비용이 덤프 순간에 몰린다. 덤프 창 p95 는 5회 모두 같은 자리의 on 창보다 크고, 창 밖은 on 보다 크지 않다. 부하 없이 손으로 뜬 덤프(10/26)는 정지 0.24ms(1회)
- **CPU** : +37%. 같은 40건에서 쇼핑몰 `#51` 은 +20% — 힙 고정 · GC 로그를 켠 차이를 나누지 않았으니 이 값으로 `#51` 을 대신하지 않는다
- **폭** : r1 · r2 는 세 조건 모두 p95 가 r3 ~ r5 보다 높다. 같은 맥북의 다른 작업을 통제하지 못했다고 보고, 같은 반복 안의 방향만 결론에 쓴다

## 5. 줄이는 방법 (후보)

| 대상 | 무엇 | 상태 |
|---|---|---|
| 에이전트 CPU · 메모리 | 전송 간격 · 샘플링 · 배치 크기는 CPU 를 못 줄였고, 계측 범위를 줄이면 서비스마다 메모리 약 20MB | 쇼핑몰 `#51` (수집) |
| 덤프 빈도 | 경보 경로는 열릴 때 한 번 + 같은 파드 5분 쿨다운 → 이번 30초 간격보다 훨씬 드물다 | 구현 (API server) |
| 덤프 정지 | 에이전트 확장 `ThreadDumper` 가 `dumpAllThreads(..., lockedSynchronizers=true, 128)` 로 뜬다. HotSpot 은 이 정보를 모으려고 정지 중 힙을 훑는다 → 끄면 짧아질 것이라는 **추정** | **안 쟀다** (수집 파트와 확인) |
