> 블로그 「GC 가 10% 를 넘으면 경보를 울려도 될까?」의 실험 · 결과 부분을 채우기 위한 근거 묶음.
> 이번 정리에서 **새 부하 · 장애 주입 · 서비스 재시작 · 설정 변경 · Slack 전송은 하지 않았다.** 쌓여 있던 데이터를 다시 읽고, 격리된 테스트만 돌렸다.

## D. 해설

### D-1. 실제 GC 로그 (스모크 회차, `gc-results/2026-10-26-smoke-256m/gclog/gc-2026-10-26_05-07-47.log`)

```
L1   [2026-10-26T05:07:47.876+0000][0.021s][info][gc] Using G1
L11  [2026-10-26T05:07:47.908+0000][0.053s][info][gc,init] Heap Max Capacity: 256M
L392 [2026-10-26T05:08:41.185+0000][53.308s][info][gc          ] GC(14) Pause Young (Normal) (G1 Evacuation Pause) 188M->61M(256M) 170.019ms
L620 [2026-10-26T05:10:03.356+0000][135.480s][info][gc          ] GC(19) Pause Young (Normal) (G1 Evacuation Pause) 211M->71M(256M) 96.955ms
L738 [2026-10-26T05:11:20.603+0000][212.723s][info][gc          ] GC(23) Pause Young (Normal) (G1 Evacuation Pause) 220M->72M(256M) 20.383ms
```

- **L392** : 부하 시작(05:08:35) 6초 뒤 첫 Young GC. 일반 Young GC 이고, 표시된 힙 사용량이 188M 에서 61M 으로 줄었으며, pause 는 170ms 다. 괄호의 256M 은 L11 의 최대 힙과 같다. 이 회차에서 가장 긴 pause 였다
- **L620** : 부하 중간. 211M → 71M, 97ms. 같은 GC(19) 의 `gc,heap` 줄(L614 ~ L618)은 Eden 140 → 0 region, Old 67 → 67, Humongous 3 → 3 이다. 이 GC 는 Old 를 줄이지 않았다 — Young GC 라 Old 를 수집하지 않은 것이지 Old 가 모두 살아 있는 객체라는 뜻은 아니다
- **L738** : 부하 끝 무렵. 220M → 72M, 20ms
- GC(15) ~ GC(23) 의 GC 뒤 사용량은 71 ~ 73M 로 평평했다. 3분 회차라 누적 여부를 말할 길이는 아니다
- 이 로그에 **Full GC · To-space exhausted · Evacuation Failure 는 없다**(검색 0건). 부하 중 pause 는 전부 `Pause Young (Normal)` 6번이었다. Remark · Cleanup · Mixed 는 기동 12초 안에만 나왔다

## E. 블로그에 넣을 문단 (초안, ~했다체)

**3절 끝에 덧붙일 것 — 우리 값은 정말 GC 시간이었을까**

> 에이전트가 센 값이 실제 GC 와 맞는지 확인하려고, 힙을 256MB 로 고정하고 GC 로그를 켠 채 3분 동안 초당 30건의 주문을 넣었다. 두 원본 점 사이(05:09:50 ~ 05:10:50)에 에이전트의 누적값은 148ms 늘었고, 같은 구간 GC 로그의 pause 는 세 번, 합 149.4ms였다. 에이전트가 쓰는 `GcInfo.getDuration()` 은 정수 밀리초라 세 pause 를 각각 내리면 148ms로 같아진다. 다만 누적값 전체는 로그보다 세 번, 134ms 적었다. 에이전트가 GC 알림을 듣기 전, JVM 이 뜨자마자 일어난 GC 를 세지 못한 것으로 보인다. 첫 1분은 앞 값이 없어 어차피 버려지므로 경보 입력에는 영향이 없었다. 이 비교는 한 번의 짧은 실행에서 얻은 것이다.

**4절 뒤 — 계산을 바꿨다 (내가 한 일과 바꾸지 않은 것)**

> 기존 조회는 팀원이 만든 누적값 빼기를 그대로 썼다. 1분마다 마지막 누적값을 남기고 바로 앞 1분 값과 뺐다. 나는 1분 집계 대신 원본 점을 읽어, 1분마다 마지막 값과 함께 그 값이 찍힌 시각을 가져오게 바꿨다. 두 점이 실제로 몇 초 떨어졌는지로 증가량을 나눈 뒤 60초치로 맞췄다. 두 점 사이에 통째로 들어간 빈 1분에는 같은 평균을 채웠고, 간격이 150초를 넘으면 전송이 빠진 것으로 보고 비웠다. 150초는 60초 전송이 한 번 밀렸다 따라잡는 최대 간격에 시각 흔들림을 더해 정한 프로젝트 값이다.
>
> 같은 입력을 넣자 결과가 달라졌다. 120초 동안 누적값이 1초에서 9초로 늘어난 경우, 이전 계산은 빈 1분을 판정 불가로 두고 다음 1분에 8,000ms를 넣었다. 바꾼 계산은 두 1분에 4,000ms씩 넣었다. 실제 데이터에서도 차이가 보였다. 10초마다 보내던 gateway 의 전송이 94초 끊겼던 1분은 이전 계산으로 1,369ms, 바꾼 계산으로 874ms였다. 메모리가 부족했던 10월 16일 08:32 의 1분은 두 점이 59초 떨어져 있어 5,704ms가 5,801ms가 됐다.
>
> 바꾸면서 잃은 것도 있다. 채운 두 1분의 4,000ms는 각 1분에 실제로 4초씩 GC 가 있었다는 뜻이 아니다. 응답에는 이 값이 채운 값인지, 원래 증가량이 얼마였는지가 없다. 채운 1분도 탐지에서는 값이 있는 1분이라 연속 횟수에 들어간다. 같은 이름표로 재시작한 JVM 의 첫 값이 이전 값보다 크면 여전히 알아보지 못한다. 고정 입력 테스트를 쓰다가 하나를 더 찾았다. 한 1분에 횟수 줄만 오고 시간 줄이 빠지면 그 1분이 0ms 로 나가, 탐지가 판정 불가가 아니라 정상으로 봤다. 이 1분은 비우도록 고쳤다.

**5절에 넣을 것 — 세 번 연속은 실제로 무엇을 셌나**

> GC 경보를 탐지에 연결하면서, 값이 없는 1분을 건너뛰지 않도록 했다. 탐지는 정착 대기가 지난 1분 끝을 빠짐없이 판정하고, 값이 없으면 판정 불가로 넣는다. 상태머신은 판정 불가를 받으면 연속 횟수를 0 으로 되돌린다. "초과, 초과, 판정 불가, 초과" 는 발화하지 않는다. 다만 상태머신 자체에는 버킷 간격 검사가 꺼져 있다. 탐지가 3분 넘게 멈췄다 돌아와 사이 버킷을 아예 평가하지 못하면, 남은 초과 세 개를 연속으로 세어 발화한다. 테스트로 이 동작을 고정해 두었다.
>
> 쌓인 10일치 쇼핑몰 GC 원본으로 같은 규칙을 다시 돌렸다. 6,000ms를 넘은 1분은 한 번도 없어 N=1 도 N=3 도 발화하지 않았다. 기준을 1,000ms로 낮추면 N=1 은 gateway 에서 4번(이전 계산이면 5번) 발화했지만 N=3 은 0번이었다. 1,000ms를 넘은 1분이 세 번 이어진 적이 없었다. 이 결과는 오탐을 줄였다는 근거가 아니다. 그 순간들이 실제 문제였는지 판단할 기준을 따로 두지 않았기 때문이다.

**6절 교체 — 45초를 나눴다**

> 원본 기록에서 같은 사건의 시각을 다시 맞췄다. 10월 16일 사건 48 은 판정 버킷이 09:15:00 에 끝났다. 탐지는 09:15:34.178 에 사건과 발송 의도를 같은 트랜잭션에 기록했다. 1분 버킷이 끝나고 30초를 기다린 뒤 15초 주기 중 첫 주기가 돈 시각이다. 스레드 덤프는 기록이 끝난 뒤 같은 주기에서 따로 불렀고, API 서버는 응답을 받은 뒤 09:15:34.680 에 저장 시각을 남겼다. Slack API 가 성공을 돌려준 시각은 09:15:45.442 였다. 그 사이 11.3초는 알림 서비스가 같은 장애의 다른 알림을 묶으려고 기다린 10초와 발송 시간이었다.
>
> 따라서 45초는 "판정 버킷 끝에서 Slack API 성공까지" 의 시간이다. 그중 34초는 판단 전에, 11초는 판단 뒤에 쓰였다. 사용자가 메시지를 본 시각은 남아 있지 않다. 같은 날 09:04 의 사건 47 에서는 덤프 요청이 503 으로 실패했지만, 같은 사건의 Slack 발송은 11초 뒤 성공했다. 덤프 실패가 경보를 막지 않는다는 것을 한 번 확인했다. 탐지는 덤프 응답을 8초까지만 기다린다. 이 한도는 탐지가 기다리는 시간이고, API 서버가 이미 시작한 덤프 작업을 멈추지는 않는다.

**7절에 넣을 것 — 실제로 압박이 왔을 때**

> 의도한 실험은 아니었지만, 10월 16일 Docker VM 메모리가 부족했던 구간이 기록에 남아 있었다. shop-order 의 1분 GC 시간은 121ms에서 2,402ms, 5,801ms로 올랐다가 71ms로 내려왔다. 같은 1분들의 요청 p95 는 427ms에서 33초까지 뛰었다. 높은 1분은 두 개뿐이었고 최대값도 10%(6,000ms)에 닿지 않았다. 그래서 10%·N=3 규칙이 켜져 있었더라도 경보는 나가지 않았을 것이다. 다만 이때는 같은 VM 의 다른 컨테이너까지 메모리가 부족해 API 서버가 죽었다. 요청 지연이 GC 때문이었다고 나눌 수 없다.
