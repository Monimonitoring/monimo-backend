# 느린 채널이 다른 채널을 늦추나 (실측)

> 2026-10-10 로컬 실측 1회씩. **측정만 했고 고치지 않았다** — 개선(채널별 실행 분리 등)은 후속 작업으로 분리한다.
> → 2026-10-27 `#250` 으로 채널별 발송 레인(bulkhead)을 넣고 같은 입력으로 전후 3회씩 다시 쟀다 (§8).
> 발송 경로는 DB 폴링이다: `DeliveryScheduler`(스레드 1개, 1초 fixedDelay) → `DeliveryWorker.pollOnce()` → 그룹마다 `process()`.

## 1. 문제와 사용자 영향

Slack 채널 하나(또는 웹훅 하나)가 느려지면, **멀쩡한 다른 채널의 알림까지 늦게 가는가?** 늦게 가면 한 고객사 웹훅이 느린 것 때문에 전체 알림이 NFR(60초)을 넘길 수 있다.

## 2. 실험

- 가짜 Slack 두 개: **느린 채널**(받는 즉시 기록, 응답을 4초 늦춤 — 요청 한도 5초 안이라 실패가 아니라 "느린 성공") · **정상 채널**(즉시 응답)
- 느린 채널에 **서로 다른 서비스** 알림 5건(묶이지 않아 그룹 5개 = 호출 5번) → 5초 뒤 정상 채널에 1건
- 같은 입력으로 느린 채널 응답 0초(기준) / 4초 비교. notifier 기본 설정(group_wait 10초 · batch 10)
- 시각은 DB(`notification_outbox.created_at` · `notification_history.sent_at`) 기준. 재현: `docs/alert/experiments/slow_channel.sh`

## 3. 결과

| | 정상 채널 알림 생성 → 발송 | 느린 채널 5건 생성 → 발송 |
|---|---|---|
| 기준 (느린 채널도 즉시 응답) | **10.78초** | 10.76 ~ 10.95초 (거의 동시) |
| 느린 채널 4초 응답 | **16.97초 (+6.19초)** | 14.22 → 18.20 → 22.15 → 26.15 → 30.14초 (**4초 간격으로 줄 섬**) |

대기열(1초 간격 표본): 느린 경우 IN_FLIGHT 가 3 → 2 → 1 로 하나씩 줄고 그동안 PENDING 3(느린 2 + 정상 1)이 그대로 기다렸다.

## 4. 원인 — 코드

1. `DeliveryScheduler.tick()` 은 **스레드 하나**에서 `while (worker.pollOnce() > 0)` 를 돈다.
2. `pollOnce()` 는 선점한 그룹들을 `forEach { process(it) }` 로 **차례로** 보낸다. Slack 호출(`sender.send`)이 끝나야 다음 그룹으로 간다.
3. 이번에는 첫 선점에 느린 그룹 3개가 들어갔고(나머지 2개는 생성이 수십 ms 늦어 group_wait 10초를 아직 못 채움), 그 셋을 보내는 12초 동안 정상 채널 알림은 준비가 끝났는데도 **다음 선점을 기다렸다** — 느린 3번째 발송 14:08:18.071 → 정상 발송 14:08:18.098 (27ms 뒤).

→ **헤드 오브 라인 블로킹**: 앞 그룹이 느리면 뒤 그룹이 채널과 상관없이 밀린다.

## 5. 최악은 (계산값, 측정 아님)

한 선점은 최대 `batch-size` 10줄이고 한 호출은 연결 한도 2초 + 응답 한도 5초까지 걸린다 → 다른 채널 알림이 **최대 약 70초** 밀릴 수 있다 (`DeliveryConfig` 가 lease 90초 > 10 × 7초 를 기동 때 검사하는 바로 그 값). 그러면 NFR(`fired_at` → Slack 60초, 지금 최대 46초)을 넘는다.

## 6. 개선 후보 (이번에 안 함)

| 후보 | 효과 | 비용 |
|---|---|---|
| 채널별 실행 분리 (bulkhead: 채널마다 스레드 · 대기열) | 느린 채널이 자기 줄만 막는다 | 스레드 · 동시성 관리, 채널 수만큼 자원 |
| 한 선점 안에서 그룹을 병렬로 보내기 | 배치 하나의 지연이 가장 느린 호출 하나로 줄어듦 | 같은 채널 동시 호출 → Slack 초당 1건 제한(429) 위험 |
| 배치를 작게 / 호출 한도를 짧게 | 최악 지연 상한이 줄어듦 | 처리량 감소 · 느린 정상 응답을 실패로 처리 |
| 이미 있는 것: 채널별 서킷브레이커(E8) | **실패**가 이어지는 채널은 호출을 멈춘다 | **느리지만 성공**하는 채널은 막지 못한다 (이번 경우) |

## 7. 확인하지 못한 범위

1회씩 · notifier 1대 · 로컬. 느린 채널 응답이 한도(5초)를 넘어 Unknown → 재시도로 쌓이는 경우, 그룹이 10개를 넘는 경우, 인스턴스 여러 대에서 서로 다른 그룹을 나눠 가지는 경우는 재지 않았다.

## 8. 고친 뒤 (2026-10-27, `#250`)

### 바꾼 것 — 채널별 발송 레인

- 선점한 줄을 **채널마다** 나눠 그 채널의 레인(`ChannelLanes`)에서 보낸다. 선점 자체는 여전히 스케줄러 스레드 하나가 한다
- 레인이 바쁜(보내는 중인) 채널은 **다음 선점에서 뺀다**(`lockDue` 의 `excluded`). 그래서 한 레인은 한 번에 선점 하나(최대 `batch-size` 줄)만 맡고, `lease > batch × (connect + request timeout)` 기동 검사가 그대로 맞는다
- 한 채널 안은 지금처럼 차례로 한 번에 하나 — 순서와 Slack 호출 제한(채널당 초당 1건)을 건드리지 않는다. §6 의 "한 선점 안에서 병렬" 을 고르지 않은 이유다
- 바쁜 채널이 `max-busy-channels`(8)이면 새로 선점하지 않는다(느린 채널이 많아도 스레드 · DB 연결이 끝없이 늘지 않게). 종료 때는 진행 중인 호출을 마저 끝내고 기록한다

### 같은 입력으로 전후 비교 (각 3회)

`slow_channel.sh` 그대로(느린 채널에 서로 다른 서비스 5건 → 5초 뒤 정상 채널 1건). 수정 전 jar(develop) · 수정 후 jar 를 번갈아 3회씩 돌렸다. 시간은 정상 작업 생성 → 가짜 Slack **수신** 시각(10/10 표는 DB `sent_at` 기준이라 기록 시간만큼 다르다). 원자료 `experiments/slow-channel-lanes-2026-10-27.txt`.

| 정상 채널 알림 생성 → 도착 | 1회 | 2회 | 3회 |
|---|---|---|---|
| 수정 전 · 기준 (느린 채널도 즉시 응답) | 11.02초 | 10.15초 | 10.16초 |
| 수정 전 · 느린 채널 4초 | **25.86초** | **21.14초** | **25.27초** |
| 수정 후 · 기준 | 10.75초 | 11.00초 | 11.07초 |
| 수정 후 · 느린 채널 4초 | **10.53초** | **10.76초** | **11.05초** |

- 수정 전에는 느린 채널 때문에 **+11 ~ +15초** 밀렸고, 수정 후에는 기준과 같다(차이 −0.2 ~ 0초). 남은 약 10초는 그룹 대기(`group-wait` 10초)다
- 수정 전의 밀림이 10/10(+6.19초)보다 큰 것은 첫 선점에 느린 그룹이 몇 개 들어가느냐에 달려서다(10/10 은 3개, 이번에는 생성 시각 차이로 더 많이 들어갔다). 최악이 배치 크기 × 호출 시간이라는 §5 계산과 같은 방향이다
- 느린 채널 5건은 전후 모두 약 16초에 걸쳐 4초 간격으로 도착했다 — 채널 안은 여전히 차례로 보낸다(의도)

### 아직 확인하지 않은 것

notifier 1대 · 로컬 · 느린 채널 하나. 느린 채널이 `max-busy-channels` 를 넘게 많은 경우, 응답이 한도(5초)를 넘어 Unknown → 재시도로 쌓이는 경우, notifier 여러 대에서 같은 채널을 동시에 보내는 경우(지금도 가능, 이번 범위 밖)는 재지 않았다.
