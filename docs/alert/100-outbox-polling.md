# 발송 경로(DB 폴링 outbox)의 지연 · DB 비용 — CDC 를 붙이기 전 출발선

> 2026-10-28 실측. 도구 `experiments/outbox_poll*`, 원본 로그는 실험 직후 임시 폴더에 있다가 재부팅으로 지워졌다 — 아래 숫자는 그때 `outbox_poll_analyze.py` 가 낸 요약을 옮긴 것이다.
> 발송 경로 설계는 `30-delivery.md`(D5 ~ D9), 그룹핑은 `50-grouping.md`. CDC 는 D5 에서 "알림 경로에 추가하지 않기로 한 것"이다.

## 1. 왜 쟀나

outbox 는 그대로 두고 **꺼내는 방법**을 폴링에서 CDC(Debezium 등)로 바꿀지 검토하기 전에, 지금 폴링이 지연과 DB 비용에서 얼마를 쓰는지부터 쟀다. outbox(업무 변경과 발송 의도를 같은 트랜잭션에 저장)와 CDC 는 대체 관계가 아니다.

## 4. 읽는 법

- **지연의 대부분은 그룹 대기(10초)다.** 그룹 대기 외 지연은 중앙값 약 0.5초, 최대 약 1초였다. 이 값은 폴링 대기 · 선점 · 전송을 합친 것이다. 선점 시각은 완료 때 `lease_until` 이 지워져 따로 남지 않는다
- **이번 단건 실험에서는 그룹 대기 외 지연이 대체로 1초 내외여서, CDC 로 줄일 여지가 크지 않았다.** 부하 · 장애 상황에서의 상한을 잰 것은 아니다. 폴링 간격만 0.2초로 줄여도 그룹 대기 0초 기준 중앙값이 610 → 174ms 가 됐다
- 판정 버킷 끝 → Slack 45초(`80-gc-time.md`, 10/16 1회)는 당시 선점 시각을 기록하지 않았다. 그중 폴링 몫이 1초 안팎이었으리라는 것은 이번 결과에 기댄 **추정**이다
- **DB 비용도 작다.** 폴링 1초에 PG 트랜잭션 초당 +2.2, 0.2초에 +5.0. 폴링 한 번당 1 트랜잭션보다 많은 이유(큐 낡음 게이지 조회 등이 섞였는지)는 나누지 않았다. Notifier CPU 1.15초/분(코어 1개의 약 2%)도 JVM 의 다른 활동을 포함한 값이다
- 그래서 **현재 알림의 지연 개선이나 DB 부하를 CDC 도입 이유로 삼기는 어렵다.** CDC 를 쓰면 안 된다는 뜻은 아니다. CDC 의 다른 이점(발송 의도를 다른 소비자도 받기, PG 조회 없이 밀어 주기)이나 비용(Kafka Connect · 커넥터 운영, 재시작 때의 중복 · 순서)은 재지 않았다

## 5. 한계

맥북 한 대 · Notifier 한 개 · 설정당 30건, 유휴는 설정당 120초 한 번. 가짜 Slack 은 바로 응답하고 Slack 의 웹훅 속도 제한(초당 1건)은 없다. 선점 쿼리 비용은 `ANALYZE` 를 한 트랜잭션 안에서 잰 값이고, 줄이 PENDING → SENT 로 바뀌며 남는 죽은 인덱스 항목 · autovacuum 의 비용은 재지 않았다. PG `LISTEN/NOTIFY` 처럼 CDC 보다 가벼운 밀어 주기는 비교하지 않았다.
